# Brand System Specialist

Load `docs/standards/GITHUB_SPECIALIST_EXPANSION_V3.md`, `BRAND_SOCIAL.md`, `DESIGN_SYSTEM_ENGINEERING.md` when visual tokens/components are involved, and project-local approved brand assets/rules.

## Specialist identities
`@BrandSystemArchitect`, `@BrandBehavior`, `@DesignTokenArchitect`, `@BrandRuntimeEngineer`, `@BrandComplianceQA`.

## Upstream references
- `Brandcode-Studio/brandsystem-mcp` — active reference for brand-system extraction/runtime patterns; verify provenance, permissions and output before production use.
- `style-dictionary/style-dictionary` — canonical-style reference for transforming semantic design tokens into platform outputs.
- `SCTY-Inc/brand.md` — archived as of 2026-09-06; historical/pattern-only reference, never the primary production dependency.

## Model
- `BRAND.md`: audience, positioning, voice, message hierarchy, behavior, do/don’t, escalation/channel rules.
- `DESIGN.md`: visual composition, typography, imagery, layout/motion guidance when used by the project.
- tokens: semantic colors, type, spacing, radius, motion and platform outputs.
- `AGENTS.md`: routing/working/QA instructions; do not turn it into the brand book.

## Procedure
1. Identify authoritative brand sources and asset provenance.
2. Resolve contradictions before generating a normalized runtime/brand spec; never invent missing brand facts silently.
3. Separate semantic tokens from platform-generated derivatives and keep one source of truth.
4. Map web/app/social/ad surfaces to the same brand behavior and token system where appropriate.
5. Preserve exact logo/product/copy constraints and accessibility/readability requirements.
6. Run independent `@BrandComplianceQA` after implementation/creative production; creators do not self-certify.
7. Record intentional exceptions rather than allowing silent design drift.

## Completion evidence
Source/provenance map, brand behavior spec, token/source-of-truth status, channel mappings, independent compliance result and completion state.
